## 零、一句话答案

| 你的问题 | 答案 |
|---|---|
| H3-Image 画风靠什么？ | **只有三条真通道**：提示词里的可见画法描述（弱）＋ **参考图（最强、零成本）** ＋ LoRA（强但重）。**没有任何 style 参数 / preset**，负面提示词**不存在**。 |
| 有没有专门的画风通道？ | **没有。** API、ComfyUI 节点、本插件三层都查过，零 style 字段。 |
| 提示词格式？中英文？ | **整幅图的完整英文描述**，顺序「用途→布局→主体动作→场景→光→相机→质感→文字」。官方要英文；中文只留给引号内的画面文字。 |
| 分级重绘能不能做？ | **能，而且模型原生支持。** mask 值直接就是去噪强度。本机已实测三档 1.0/0.5/0.2 → 改动量 121 / 3.1 / 0.64。**但只在我们自己的管线里需要额外工作**（模型本身不吃 mask，详见 §三）。 |
| 分块 / 分层 / 多人拆分？ | 分块：`Attention Couple` 系在 H3 上**会静默失效**（H3 没有 cross-attention）。分层：图层扩散类绑定 SD/Flux 底模，**不能直接用**。多人：**`<Picture 1..16>` 多参考就是官方原生赛道**，这是最该走的路。 |

## 一、H3-Image 画风控制

### 1.1 三条真通道

| 通道 | 判定 | 实际效果 | 关键细节 |
|---|---|---|---|
| **提示词 style words** | 有（永远在场） | **中偏弱** | 必须写「怎么画」：`flat cel shading` / `two-tone shadows` / `clean dark linework`。只写 `anime style`、`high quality` 会被模型挑成 3D 混血 |
| **参考图 `<Picture N>`** | 有 | **最强、最省** | 一张「已经是目标画风」的图 > 任何风格文字。**接 VAE** → 参考图被锚定为 reference latent（像素级约束）；**不接 VAE** → 只经文本编码器（更松，更适合「只借画风」） |
| **LoRA** | 有（仅本地） | 强但重 | 需要触发词；**总强度 > 1.5–2.0 会出坏图**；Civitai 上 `baseModel=MiniMax H3 Image` 仅 **58 个** |

### 1.2 被排除的「伪通道」

| 容易误判为画风开关 | 为什么不是 |
|---|---|
| 步数 / CFG / sampler | 6 步由 checkpoint 的 6 个 PDD 头决定，cfg 恒 1；传别的值 API 直接 400 |
| 负面提示词 | **不存在**。SGLang 对 `negative_prompt` 返回 400；ComfyUI 用 `BasicGuider`，**没有 negative 分支** |
| prompt_optimizer / enhance | 那是 PE（提示词增强器）开关，改的是「提示词被改写成什么」，不是模型侧旋钮 |
| ControlNet | H3-Image **目前没有可用 ControlNet**。社区把视频侧 ControlNet 接过来失败（"perturbs, never steers"） |
| 换 VAE | 属于后处理式观感修改，不是画风控制 |

### 1.3 官方 API 字段核对（确认没有 style）

对 `/v1/images/generations`、`/v1/images/edits`、`/v1/h3_image_context_ir` 三份 OpenAPI 逐字段核对：
`model` / `prompt` / `images` / `size` / `aspect_ratio` / `area` / `n` / `output_format` /
`response_format` / `stream` / `disable_prompt_enhanced`。
**没有任何 `style` / `style_preset` / `style_id` 字段。**

这与上一代 `image-01` 一致，是 MiniMax 的产品取向：**画风完全交给提示词与参考图**。

### 1.4 市面上的画风实践 vs 能借鉴什么

| 模型 | 画风控制主要手段 | 对 H3-Image 可借鉴？ |
|---|---|---|
| SD1.5 / SDXL | LoRA 生态巨大 + 负面提示词 + ControlNet | LoRA 思路可用；**负面与 ControlNet 不可用** |
| FLUX.1 | 提示词 + LoRA（无负面，cfg 蒸馏） | **最接近**。FLUX 的「用完整自然语言描述」写法可直接借用 |
| Qwen-Image | 强中文 + 提示词 | 中文优势来自训练，H3 不具备 |
| 社区 H3-Image 实践 | 提示词画法词 + 画风 LoRA + 参考图 | 三者我们都有对应基础设施 |

**关键情报**：base H3 的 2D 输出**天然偏 3D**（滑块 LoRA 作者原话）。所以本插件已有的 5 套 2D 画风
必须显式加「反 3D 化」约束（`NOT 3D`、`no 3D render`、`flat 2D only`），否则会被拉向 3D 混血。

## 二、H3-Image 提示词格式与要求

### 2.1 格式：整幅图的完整英文描述

官方推荐顺序：

```
用途 → 布局 → 主体与动作 → 场景 → 光线 → 相机 → 质感 → 画面上的文字
```

**风格词放最后**，且必须用**可观测的画法词**：

- ✅ `flat cel shading, two-tone shadows, clean dark linework, no gradients`
- ❌ `premium, cinematic, masterpiece, high quality`（无信息量，模型自己挑）

### 2.2 长度

| 侧 | 上限 | 我们本地 |
|---|---|---|
| 官方 API | 4096 **tokens**（prompt 字段可 32000 字符，但关 PE 时只读前 ~4096 token） | — |
| 本地 ComfyUI | Qwen3-VL 32B 上下文充裕 | 插件设为 **4096 字符**（更紧，超长 400 拒绝不截断） |

### 2.3 中英文

- **官方要求英文**：「Write the description in English. Text that appears in the image keeps its own language.」
- **中文能出图但遵循度明显更低**。官方 API 上「中文可用」很大程度是因为前置的 Context-IR / PE 会翻译成英文。
- **我们本地没有 PE**，中文原样进 Qwen3-VL（不加 chat template）→ **中文风险被放大**。

**结论**：中文需求应当由调用方（agent / 编译器）翻成英文长描述再提交，而不是直接喂中文。

### 2.4 文字渲染（lettering）

- 每个词进**引号** + 说明位置/字号：`a chalkboard by the door reading "OPEN LATE"`
- 短字符串最准；小字仍是乱码纹理
- 不要文字就明确写 `The image contains no text, letters or numbers.`
- 反直觉：**8MP 比 4MP 更容易拼错小字**

### 2.5 提示词增强器（PE）—— 我们缺的那一环

官方两个模板在采样器**前面**都有一个 prompt expander（官方是 Qwen3.8-27B FP4，模板用 Qwen3.5 9B W4A8），**默认开启**，把简短指令改写成详细英文描述。

两份实测结论看似矛盾，其实一致：

| 情况 | 开 PE | 关 PE |
|---|---|---|
| 短提示词 / 随手一句 | **更好**（拼写、颜色、排除项都对） | 差 |
| 已写全的详细提示词 | **更差**（会覆盖你定好的细节） | **更好** |

**我们本地工作流只有 11 个节点，确认没有 expander**。这意味着：
「展开提示词」这件事必须由我们自己承担 —— 这正是插件里提示词编译器该做的事，但目前**图像侧完全没有对应实现**（视频侧有完整的六段式编译器）。

## 三、局部重绘提示词与「分级重绘」

### 3.1 一个必须先澄清的事实

> **H3-Image 模型本身不吃 mask。**

从源码看，`MiniMaxH3ImageConditioning` 的输入只有 `clip / prompt / width / height / vae / images`。
模型的图像编辑能力来自 **`<Picture 1..16>` 参考图 + 提示词**，**没有 mask 输入**。

我们现在的「局部重绘」是**自己在外层搭的封装**：
```
mask → 算 bbox → 裁剪放大 → 用 mask 做 SetLatentNoiseMask → 采样 → 贴回原图
```
`SetLatentNoiseMask` 是 ComfyUI 的核心节点，不是 H3 特有的。**这套封装是有效的**（本机已验证选区外逐像素保真），
但要清楚：**它不是模型的原生 inpainting 通道**。

### 3.2 分级重绘：模型原生支持，且已实测

**源码证据**（`comfy/ldm/minimax/model.py:757-765`）：

```python
m = mask_row_values(denoise_mask[0, 0], latent_t, lat_h, lat_w)
rows_t = (1.0 - m * sigma_v).clamp(max=t_pin_v)
#   m = mask 值（0..1），sigma_v = 当前噪声水平
#   mask=1.0 → 该行按完整 sigma 去噪（完全重绘）
#   mask=0.5 → 该行按半个 sigma 去噪（半重绘）
#   mask=0.0 → 该行被 clamp 到 cond timestep（完全保留）
```

**mask 的浮点值被原样当作逐行去噪强度**，不是二值化。下游 `out[0] = out[0] * denoise_mask` 再做乘法门控。

另外 `mask_row_values` 会做 **2×2 最大池化**下采样到 patch 网格 ——
所以分级的最小粒度是 **2×2 latent patch（约 32×32 像素）**，不是逐像素。

**本机实测**（1024² 源图，full 模式，同一提示词 `a field of bright red poppies`）：

| mask 值 | 实际去噪强度 | 改动量（mean / max） |
|---|---|---|
| 1.00（全重绘） | 6 步全跑 | **121.4 / 232** |
| 0.50（半重绘） | 约 3 步 | **3.1 / 89** |
| 0.20（轻重绘） | 约 1 步 | **0.6 / 34** |

渐变 mask 的横向剖线（8 段，左→右）：
`[77.5, 19.0, 6.1, 2.0, 1.1, 1.1, 0.8, 0.5]` —— **单调递减，分级成立**。

**但有一个重要的非线性**：mask 0.5 的实际改动量只有 3.1（约为 1.0 的 2.5%），而不是直观的「一半」。
原因是 6 步 PDD 蒸馏下，`1.0 - m*sigma` 落在哪个 sigma 区间决定用哪个预测头，
**0.5 正好落在头部交界处，效果会塌陷**。所以：

- `0.85–1.0` → 明显改动（可用）
- `0.55–0.75` → 轻微改动
- `0.3–0.5` → **几乎不可见**（塌陷区）
- `< 0.3` → 等同保留

**可用的实践分级**建议按实测校准，而不是线性直觉：

| 档位 | mask 值 | 语义 |
|---|---|---|
| 完全重绘 | 1.0 | 按提示词完全重新生成 |
| 强 | 0.85 | 大改，保留大致构图 |
| 中 | 0.7 | 中等改动 |
| 轻 | 0.55 | 小幅修饰 |
| 保留 | 0 | 完全不动 |

### 3.3 现在管线里缺什么

要让分级重绘可用，还需要补三块（**尚未实现**）：

1. **前端**：画笔的 `opacity` 已经存在（`brush.ts` 有 `opacity` 字段，UI 没暴露），
   加一个「笔压 / 强度」滑块，让用户涂出不同灰度，即可直接产出分级 mask。
   目前 UI 只有 size / hardness / 擦除，涂出来永远是纯白 255。
2. **后端**：`GrowMask(+16)` 和羽化会**改写 mask 的值域**，分级信息会被破坏。
   分级模式下必须跳过 grow，羽化只作用于边界过渡。
3. **校验**：需要按上表把用户选的「强度档」映射到 mask 值，而不是让用户直接填 0–255。

### 3.4 局部重绘的提示词该怎么写

因为模型**没有 mask 感知**，它只知道「我要按提示词改这张图」，所以：

- **必须描述「改完之后整幅图是什么样」**，而不是「在那个框里画什么」。
  这是最常见的使用错误。写 `a red lantern` 可能得到「整幅图变成一个红灯笼」；
  正确写法是 `a night street with a red paper lantern hanging from the eaves, everything else unchanged`。
- **必须加保留句**：`Keep everything else exactly the same.`（官方编辑示例的原话）
- 指向参考图时用 `<Picture 1>`：`Replace the car in <Picture 1> with the one in <Picture 2>.`
- **禁止链式多轮编辑**：实测第 3 轮开始崩、第 10 轮人已认不出。

## 四、分块 / 分层 / 多人拆分

### 4.1 分块绘制（区域控制）

**核心阻断（已在本机源码验证）**：

| 事实 | 验证方式 | 后果 |
|---|---|---|
| H3 **没有 cross-attention** | `comfy/ldm/minimax/*.py` grep `CrossAttention` → **0 命中** | 单流 packed 序列 `[text｜参考图｜目标图]`。**Attention Couple / Forge Couple / Region Genie 全部静默失效**——图照常出，区域不生效，不报错 |
| H3 **硬拒绝 batch>1** | `model.py:721` `raise ValueError("MiniMax H3 supports batch size 1")` | 内置 area 条件把多区域 concat 成 batch → 两个同尺寸区域**直接 500** |
| 内置 `ConditioningSetArea` 坐标写死 `//8` | `nodes.py`：`(height // 8, width // 8, y // 8, x // 8)` | H3 VAE 是 **16×** 下采样 → **1024px 的区域实际变成 2048px**，必然错位 |
| `VAEDecodeTiled` 对 H3 无效 | `vae.py:581` H3 VAE 内部始终 tile_size=256，忽略外部参数 | 参数被无视且不报错 |

**可行的路**：

- ✅ **`<Picture 1..16>` 多参考编辑** —— 官方原生，这也是「多人合成」最该走的路
- ✅ `ConditioningSetAreaPercentage`（与下采样倍率无关），但多区域会撞 batch 限制
- ⚠️ 在 `optimized_attention_override` 里写 H3 专属 per-token mask —— 唯一结构上正确的区域控制方案，
  但**需要改 ComfyUI 侧代码**，且「6 步蒸馏 + 注意力分区」**没有任何公开先例**
- ❌ 原样接 Attention Couple 系、原版 MultiDiffusion 包（假设 4-D image latent）

### 4.2 分层绘制

- 主流做法是**事后拆层**（生成整图 → 分割抠图分层），不是「一次生成多层」
- **LayerDiffuse 类绑定 SD1.5/SDXL/Flux 底模，不能套到 H3**
- IC-Light（光照重打）同样按底模绑定
- Qwen-Image-Layered 的节点在 ComfyUI 0.45.0 核心里，但**缺权重**
- **对「多角色不串脸」帮助有限**：分层解决的是「前后景分离」，不是「多个身份互不污染」

### 4.3 多人 / 复杂构图拆分再拼合

**业界三种主流路线**：

| 路线 | 做法 | 对 H3-Image |
|---|---|---|
| **参考图条件化**（推荐） | 每个角色一张参考图 → `<Picture N>` → 提示词里按标签指派 | ✅ **官方原生赛道**，零改造 |
| **各出单人再合成** | 分别出单人图 → inpaint 融合 / 光照统一 | ⚠️ 需要额外的合成与光照统一，工作量大 |
| **区域提示词** | 分区域注入不同条件 | ❌ 见 §4.1，H3 上失效 |

**身份一致性的三条路**：

| 方案 | 强度 | 代价 |
|---|---|---|
| 角色 LoRA | 最强、最稳 | 需要训练（Unsloth 60 张 / 150 步 ≈ 100 秒，很便宜） |
| IP-Adapter / PuLID / InstantID | 中强 | 这些绑定 SD/Flux 底模，**H3 上不可用** |
| `<Picture N>` 参考编辑 | 中 | **零成本，官方原生** ← 优先用这个 |

### 4.4 对 H3-Image 的可行性总表

| 方案 | 判定 | 说明 |
|---|---|---|
| `<Picture 1..16>` 多参考编辑 | ✅ **立即可用** | 已被官方验证的多角色赛道 |
| 现有 inpaint crop + 贴回 | ✅ **已实现且实测有效** | 选区外逐像素保真 |
| 分级重绘（mask 值 = 强度） | ✅ **模型原生支持，已实测** | 只需补前端画笔与跳过 grow |
| H3Kit 高清分块采样 | ✅ 本机可用 | 只解决**显存**，不做区域控制 |
| `ConditioningSetAreaPercentage` | ⚠️ 要改造 | 需规避 batch 限制（推断，未实测） |
| per-token mask 区域控制 | ⚠️ 需改 ComfyUI | 唯一结构正确的方案，但无先例 |
| Attention Couple / MultiDiffusion | ❌ **不适用** | H3 无 cross-attention |
| LayerDiffuse / IC-Light | ❌ **不适用** | 绑定 SD/Flux 底模 |
| ControlNet | ❌ **不适用** | H3-Image 无可用的 |

## 五、结论与建议（按 ROI 排序）

| # | 建议 | 理由 | 工作量 |
|---|---|---|---|
| 1 | **把「参考图当画风锚」做成一等路径** | 唯一「最强且零成本」的画风通道，现在只是能用、没被当成主路径 | 小 |
| 2 | **图像侧补提示词编译器** | 视频侧有完整六段式编译器，图像侧完全空白；且我们缺 PE，必须自己承担展开 | 中 |
| 3 | **分级重绘**：前端加笔压/强度、后端分级模式下跳过 grow | 模型原生支持，实测成立，现在是完全没暴露 | 小 |
| 4 | **图像提示词强制英文** | 本地无 PE，中文风险被放大 | 小 |
| 5 | 2D 画风加「反 3D 化」约束 | base H3 的 2D 天然偏 3D | 极小 |
| 6 | 多角色走 `<Picture N>`，不碰区域提示词 | 后者在 H3 上静默失效 | 无需改造 |
| 7 | 画风 LoRA 生态跟踪（现 58 个） | 有需要再训练，别先做 | 观望 |

**明确不建议做的**：接 Attention Couple 系 / 分层扩散 / ControlNet / 靠 CFG 或负面提示词换服从度 ——
四个方向在 H3-Image 上分别因为「无 cross-attention」「绑定底模」「没有可用权重」「cfg 恒 1」而不可行。
