## 一、分块绘制

### 1.1 社区/官方「区域提示词 / 分区生成」方案盘点

| 方案 | 代表实现 | 机制 | 支持模型 | 已知限制 |
|---|---|---|---|---|
| **Conditioning (Set Area)** 系列（ComfyUI 内置） | [`nov nodes.py:187` ConditioningSetArea](https://docs.comfy.org/ja/built-in-nodes/ConditioningSetArea)、`ConditioningSetAreaPercentage`、`ConditioningSetAreaStrength`、`ConditioningSetMask` | 给 conditioning 挂 `area` / `mask` 字段，采样时**把 latent 按矩形裁小、单独前向一次**，再按像素权重加权累加 | 任何走 UNet 的 SD1.5/SDXL/SD3 | 每区一次完整前向（N 区 ≈ N 倍算力）；区边界是硬切的，无明显过渡；`area` 单位是 `/8` 的 latent（源码硬编码，见 1.2） |
| **Attention Couple（PPM）** | [pamparamm/ComfyUI-ppm](https://github.com/pamparamm/ComfyUI-ppm) | 在**交叉注意力**里按 mask 切分每个 region 的 text token，一条轨迹内完成 | README 列出 SD1 / SDXL / Anima（FLUX 的 NegPip 已标注 Unmaintained） | 依赖「有独立 cross-attention 模块」的 UNet 结构 |
| **Attention Couple（prompt-control）** | [asagi4/comfyui-prompt-control 文档](https://github.com/asagi4/comfyui-prompt-control/blob/master/doc/attention_couple.md) | 用 ComfyUI hook 系统改写成 `COUPLE MASK(...)` 语法 | SD 系（基于 PPM 实现） | 官方文档原话：*"attention coupling is not guaranteed to perfectly limit the effect of your prompt to the masked area"* —— **区域是软约束，不是硬边界** |
| **Forge Couple** | [Haoming02/sd-forge-couple](https://github.com/Haoming02/sd-forge-couple) | Forge WebUI 的 Attention Couple 实现，Basic/Advanced/Mask/Tile 四种模式 | SD1 / SDXL / Anima | README 明说 *"Regions are suggestions, not strict boundaries"*；`Hires. fix` 期间不生效（需开 compatibility toggle）；图像**每个像素都必须有权重**，否则报错 |
| **Region Genie** | [TheGhostOfSmittyWerbenjagermanjensen/ComfyUI-Region-Genie](https://github.com/TheGhostOfSmittyWerbenjagermanjensen/ComfyUI-Region-Genie) | 画布画 region，转成 attention patch；带 `separation` / `until` 两个旋钮 | MOSS-Image、Ideogram 4、Krea 2、Flux.1/2/Klein、Anima、SDXL、SD1.5 | README 自述质量取舍：`separation` 高 → 风格各归其位但**接缝像拼贴**；低 → 融合自然但细节互串。`until` 低 → 只有前几步分区 |
| **Regional Prompter / Painter** | [eimiss/comfyui_eimiss_nodes](https://github.com/eimiss/comfyui_eimiss_nodes) | 涂色分区图 + `BREAK` 分段 prompt；两种模式 `mask bounds` / `full image` | illustrious、anima 等「支持 masked conditioning」的模型 | README 自述 `mask bounds` 的硬伤：*"each region is drawn at its own size, so a character in a small region can come out as a fragment"*；`full image` 约 3× 耗时（4 区），且各区光照/透视可能互相矛盾 |
| **DiT 专用 attention 区域**（Flux/Z-Image） | [arXiv:2411.02395 Training-free Regional Prompting for DiT](https://arxiv.org/abs/2411.02395)、[Region Attention 节点](https://comfy.icu/node/RegionAttention)、[BV Regional Z-Image Attention](https://comfy.icu/node/BV-Regional-Z-Image-Attention) | 在 DiT 的**联合注意力**上做 per-token mask，需要额外调 `base ratio` / 注入步 β / 注入层数 T | FLUX.1、Z-Image Turbo | 节点描述直说 *"Regional prompting techniques don't transfer across architectures"*；BV 节点**按架构拒绝**（reject FLUX/SDXL/Anima）；且因 CFG=1，*"your regional quality is almost entirely prompt-and-geometry driven"* —— 没有负面提示词可以借力 |
| **ARMD（Adaptive Regional Mixture of Diffusers）** | [lucasgattas/ComfyUI-Egregora-ARMD](https://github.com/lucasgattas/ComfyUI-Egregora-ARMD) | core region + context region + feather 写回，共享画布 denoise | 主打 SDXL / Z-Image Turbo | README 自认：*"practical open-source method and experimental workflow, not as a fully benchmarked universal solution"* |

**小结**：业界方案分两族——**「裁切前向 + 加权融合」**（ComfyUI 内置 area、Regional Prompter）与**「注意力分区」**（Attention Couple 系、DiT regional）。前者分辨率/架构无关但费算力、边界硬；后者省算力、过渡自然，但强依赖模型有「可被外部 patch 的注意力结构」。

### 1.2 机制真相：内置 area 条件到底做了什么（源码）

这一段是后面可行性判断的基础，全部来自本机 `comfy/samplers.py`：

1. `get_area_and_mult()`（`comfy/samplers.py:33`）把 `area` 追加成与 latent 维数对齐的元组，然后 `input_x.narrow(...)` —— **把 latent 真的裁下一块**，用这块单独跑一次 `model.apply_model`。
2. 每个 cond 的权重 `mult = mask * strength` 与输出一起累加，最后 `out_conds[i] /= out_counts[i]`（`comfy/samplers.py:353-354`）—— 即**按像素加权平均 N 次前向结果**。
3. 完全不重叠的区域不会被归一化补偿：源码注释与社区文档都指出未覆盖区会出现「MultiDiffusion 棕色 / Mixture of Diffusers 噪点」类伪影（[A1111 中文 README](https://github.com/zxchh-7736/multidiffusion-upscaler-for-automatic1111/blob/main/README_CN.md)）。
4. `ConditioningSetArea` 的坐标换算写死为 8 倍下采样：

   ```python
   # nodes.py:205
   c = node_helpers.conditioning_set_values(conditioning,
       {"area": (height // 8, width // 8, y // 8, x // 8), "strength": strength, ...})
   ```

   而 `ConditioningSetAreaPercentage` 走的是百分比→latent 尺寸换算（`comfy/samplers.py:768-780`），**与下采样倍率无关**。
5. `ConditioningSetMask` 的 mask 会被 `common_upscale` 到 latent 分辨率（`comfy/samplers.py:788-792`），`set_area_to_bounds` 时再取 AABB 当 area。

**关键推论（源码 + 推断）**：内置 area 条件是**按 latent 网格裁剪**的。H3-Image 的 latent 是 `[1, 24, 1, H/16, W/16]`（`comfy_extras/nodes_minimax_h3.py:745`，VAE `space_down=(2,2,2,2,1,1)` → 16×，`comfy/ldm/minimax/vae.py:577`）。所以 `ConditioningSetArea` 里写死的 `//8` 会让「1024px 宽的区」在 H3 上实际变成「2048px 宽的区」——**区域尺寸与偏移全部 ×2**。只有 `ConditioningSetAreaPercentage` 这一个是倍率无关的。

### 1.3 大图超分里「分块生成再拼合」的标准做法

标准链路是三件事分开的，不要混为一谈：

| 环节 | 做法 | 代表实现 | 接缝处理 |
|---|---|---|---|
| **采样分块** | 每一步 denoise 都在重叠 tile 上跑，按权重把每 tile 的 **预测**（不是最终像素）融合回全图 latent | [MultiDiffusion (arXiv:2302.08113)](https://arxiv.org/abs/2302.08113)、[Mixture of Diffusers (arXiv:2302.02412)](https://arxiv.org/abs/2302.02412)、[comfyorg/comfyui-tiled-diffusion](https://github.com/comfyorg/comfyui-tiled-diffusion) | `tile_overlap` + 权重窗（高斯 / 金字塔 / 线性）。官方 README 给了调试法：**先把 `tile_overlap` 设 0、`denoise` 设 1，看见接缝，再调参数** |
| **VAE 分块** | 编解码按 tile 走，但 GroupNorm 统计量要跨 tile 归一 | [Tiled VAE（multidiffusion-upscaler DEVELOPER.md）](https://github.com/pkuliyi2015/multidiffusion-upscaler-for-automatic1111) | 核心技巧是**先汇总全部 tile 的 GroupNorm mean/var 再统一 apply**，decoder/encoder 各 pad 11/32 px，zigzag 顺序减少搬运 |
| **像素贴回** | 裁切→采样→按软 mask 贴回原图，选区外逐像素不动 | [lquesada/ComfyUI-Inpaint-CropAndStitch](https://github.com/lquesada/ComfyUI-Inpaint-CropAndStitch) | `mask_blend_pixels` 生成带羽化的贴回权重 |

经验数值（社区经验，非官方基准）：
- MultiDiffusion 重叠建议 32–48 latent px，Mixture of Diffusers 16–32（A1111 README 中文版）。
- ARMD 给的比例是 **overlap ≈ tile 的 1/3~3/8，feather ≈ 1/16~1/8**（1024 tile → 384 / 64）。
- 接缝「看不见」不等于「不存在」：tile 边界是**纹理相位跳变**，锐化只会让它更明显（[versely 分析](https://www.versely.studio/blog/a-faint-grid-across-your-upscale-tile-seams)、[archigenai](https://archigenai.com/comfyui-4k-tile-seam-qa-architects-2026.html)）。

已知失败模式（社区经验）：
- **Tiled VAE `fast` 解码器会带伪影**，SDXL 上实测更明显，解法是关掉 fast decoder（[discussion #397](https://github.com/pkuliyi2015/multidiffusion-upscaler-for-automatic1111/discussions/397)）。官方 README 也承认 fast 会「slightly higher contrast and brightness」。
- **tile 数量上去后接缝才显形**：4MP 时几块，17MP 时好几倍块数，原本看不见的缝开始出现（[SeedVR2 讨论](https://huggingface.co/lvladikov/SeedVR2-1.4B/discussions/1)）。
- **SpotDiffusion** 用「每步随机平移去噪窗口」消除接缝，但作者自己标注 *experimental / in testing*，且「`tile_overlap=0` 才划算，否则不如用别的策略」（官方 README 原话）。

### 1.4 对 cfg=1 / 无负面 / 少步蒸馏模型的适用性

这是本节最重要的部分。分三层：

**(a) 「无负面提示词」本身不是致命伤。**
内置 area 条件、Attention Couple、Regional Prompter 的主路径都只作用在**条件流**上，不需要 uncond 分支。cfg=1 时 ComfyUI 直接跳过一次 uncond 前向：

```python
# comfy/samplers.py:610-613
if math.isclose(cond_scale, 1.0) and model_options.get("disable_cfg1_optimization", False) == False:
    uncond_ = None
```

（本机 0.45.0 源码；[musetta.ai 的解释文](https://musetta.ai/blog/comfyui-negative-prompt-not-working-cfg-1-nag) 与之一致。）所以「负面提示词失效」≠「区域提示词失效」。

**(b) 但「借负面提示词做区域隔离」这条路彻底断了。**
大量 SD 时代的区域工作流靠「在区域外写 negative」来压制入侵。cfg=1 下没有 negative 通道，相当于**把区域约束从双向降级成单向**——只能「往这里推」，不能「从这里推走」。BV 的 Z-Image 节点描述把这个后果讲得最直白：因为 CFG=1，*"your regional quality is almost entirely prompt-and-geometry driven"*。

**(c) 蒸馏少步模型对「多次前向」尤其不友好。**
- 内置 area 条件 = N 个区 N 次完整前向。H3-Image 6 步、2048² 单张约 148s（本机实测数据见 `docs/H3-IMAGE-接口与LoRA使用手册.txt`），4 区就是 4×。
- 更严重的是**强开 CFG 会崩**：把 cfg 从 1 拉到 2.8 跑 4 步 SD3.5 Turbo，会出现概念错乱与严重过饱和（[VSF 论文 arXiv:2508.10931](https://browse-export.arxiv.org/pdf/2508.10931) 的反例图）；原因是蒸馏时教师的高 CFG 已经被蒸进权重，推理再开一遍等于「二次加持」（[知乎讨论](https://www.zhihu.com/question/1997709351998215043/answer/2011782113268084814)）。
- 结论：**「加 CFG 换区域服从度」这条退路在 H3 上不存在**。

**(d) 想让 cfg=1 模型重新获得负面引导，官方给了 NAG，但它有硬前提。**
ComfyUI 内置 `NAGuidance`（`comfy_extras/nodes_nag.py`，`is_experimental=True`，节点描述原文：*"enabling negative prompts on distilled/schnell models"*）。它需要两个前提：
1. `cond_or_uncond` 里必须同时有 0 和 1 —— 即必须**真的跑了 uncond 分支**；
2. 补丁挂在 `set_model_attn1_output_patch` 上 —— 即模型**必须有 `CrossAttention` 模块**。

源码里它显式调用 `m.disable_model_cfg1_optimization()` 来强制不跳过 uncond。**所以 NAG ≠ 「cfg=1 也能用负面」；NAG 的真实语义是「把 CFG 重新打开，但用注意力归一化抵消掉过饱和」**，代价是每张图多一次完整前向。第三方 Krea2 NAG 节点（[comfy.icu](https://comfy.icu/node/Krea2NormalizedAttentionGuidance)）也明说这是「不花 CFG-1 速度」的 workaround，实际仍要算第二遍。

## 二、分层绘制

### 2.1 业界两条路线

**路线 A：先生成图层，再合成（原生 RGBA）**
代表是 LayerDiffuse：把 alpha 编码成「latent 偏移」注入既有 latent 流形，VAE 不动、UNet 不动，只训一个透明编码器/解码器。论文 [arXiv:2402.17113](https://arxiv.org/abs/2402.17113)（SIGGRAPH 2024）给出关键数据：**97% 用户偏好原生透明输出而非「先生成再抠图」**，且质量被评与 Adobe Stock 商业透明素材相当。这是目前唯一有对照实验支撑的分层出图论证。
工程实现：[huchenlei/ComfyUI-layerdiffuse](https://github.com/huchenlei/ComfyUI-layerdiffuse)（Apache-2.0 代码 + OpenRAIL-M 权重），核心两节点 `LayeredDiffusionApply` + `LayeredDiffusionDecodeRGBA`。

**路线 B：先生成整图，再分解/抠图**
代表是 [Qwen-Image-Layered](https://qwen.ai/blog?id=qwen-image-layered)：端到端把一张 RGB 拆成可变数量（3/4/8）的 RGBA 层，支持递归再拆；ComfyUI 已原生支持（[ComfyUI 官方博客](https://blog.comfy.org/p/qwen-image-edit-2511-and-qwen-image)），核心节点 `EmptyQwenImageLayeredLatentImage` 在**本机 0.45.0 的 `comfy_extras/nodes_qwen.py` 里已经存在**（源码确认，见 5.1），但本机未装 qwen 权重。学术侧同类工作：[MRT (CVPR 2026)](https://mrt-cvpr.github.io/)、[LASAGNA](https://paper.dou.ac/p/2601.15507v1)。

**路线 C（没人做成产品）：全模型 4 通道重训**
把 VAE 的 `conv(3→64)` 改成 `conv(4→64)` 技术上很简单，但要重训 UNet/DiT + 重学文本对齐 + 收集带真值 alpha 的数据，成本是「数十亿张图」（[Haven Studios 的工程说明](https://havenstudios.com/en/blog/adapting-stable-diffusion-to-create-rgba-imagery)）。所以所有厂商都选了 A 或 B。

### 2.2 ComfyUI 生态现状

| 方案 | 状态（2026-11） | 能吃哪些底模 | 关键坑 |
|---|---|---|---|
| ComfyUI-layerdiffuse | **冻结在 2025-02-25**，Flux 支持 issue #121 至 2026-04 仍 stale | SD1.5 / SD2.x / SDXL | 重训过的 SDXL 变体（Pony/Noobai/Illustrious）会让 alpha 漂移，官方建议改用 Conv 注入权重；decode 硬性要求 `H%64==0` |
| RedAIGC/Flux-version-LayerDiffuse | 独立仓，2025-05 最后更新 | Flux.1 dev/schnell | 自带 `TransparentVAE.pth`，权重走另一套许可 |
| Qwen-Image-Layered | **ComfyUI 原生**，官方模板 | 专用模型 | 不是「给任意模型加 alpha」，是另一个模型 |
| AlphaVAE（[katsut/ComfyUI-AlphaVAE](https://comfy.icu/extension/katsut__ComfyUI-AlphaVAE)） | 社区，8 个月 | FLUX（换 VAE） | 同样是换 VAE 思路，需对应底模 |
| 分解式：[Comfyui-HAIGC-PSD](https://github.com/HAIGC/Comfyui-HAIGC-PSD)、[ComfyUI-PSD-Layers](https://github.com/coeyes/ComfyUI-PSD-Layers) | 活跃 | 任意（纯 IO） | 只负责存/读 PSD，不做生成 |

**注意一个经常被搞混的点**：`JoinImageWithAlpha` / `SplitImageWithAlpha`（`comfy_extras/nodes_compositing.py:165-219`）是**把已有 mask 拼成 RGBA**，不是生成 alpha。很多「透明出图」教程其实只是「生成 → RMBG → Join」，属于路线 B 的后处理。

### 2.3 分层对「多角色不串脸」有没有用？

**有帮助，但帮助来自「物理隔离」，不是来自「模型变聪明」**，而且证据质量参差：

- **强证据（论文级）**：LayerDiffuse 的 97% 偏好数据说明「原生分层」在边缘/半透明/发丝上明显优于事后抠图。但注意：**它证明的是「alpha 质量」，不是「身份一致性」**。
- **中等证据（可复现工作流自述）**：[MOSS-MultiID](https://github.com/shutong-queyue/ComfyUI-MOSS-MultiID) 的 B 链「一趟分区域」展示「左边推写实、右边保持平涂，交界无难看接缝」；A 链「两趟锁身份」展示「只有接了滤镜的编号换脸，未接的保持原生」。这是**节点作者自述 + 配图**，不是盲评。
- **弱证据（营销/二手）**：有中文博客称「多人同框分层后身份保持率从 35% 提升到 92%、遮挡正确率 40%→90%」([2ds.cn](https://www.2ds.cn/ai-animation/crowd-scene-occlusion/))。**该文没有给测试集、没有给基线定义、且对象是视频模型**，我把它标为**低可信度社区经验**，不建议作为方案依据。
- **反证**：Saya Couple 作者自己写明 *"Dynamic ownership is a heuristic... they were not A/B validated by blind review"*（[alphaziod/saya-studio-x-couple](https://github.com/alphaziod/saya-studio-x-couple)）。区域性方案普遍缺盲评。

**结论**：分层/分区的真实收益是**「改一个角色不牵动另一个」**（可编辑性、可重绘性），这有工程保证；「身份保持率提升 N 倍」这类数字目前没有可信的公开基准。

## 三、多人拆分再拼合

### 3.1 主流三条合成路线

| 路线 | 做法 | 工具 | 代价 / 失败模式 |
|---|---|---|---|
| **单人出图 → 贴入 → inpaint 融合** | 各角色单独出图（最好带 alpha），贴到背景上，再用 inpaint 把边缘与地面/投影融进去 | [Flux-insert-character](https://github.com/kinelite/Flux-insert-character)（Flux fill + redux + ReActor + Inpaint Crop/Stitch）、[CropAndStitch](https://github.com/lquesada/ComfyUI-Inpaint-CropAndStitch) | 透视/接触阴影/边缘光要重画；inpaint 裁剪块太小会把人物画成碎片 |
| **光照统一（relight）** | 贴好后用重打光模型把前景的光向背景对齐 | [IC-Light](https://github.com/lllyasviel/IC-Light)（[ComfyUI 原生实现](https://github.com/huchenlei/ComfyUI-IC-Light-Native)、[Easy-Use 封装](https://comfy.icu/node/easy-icLightApply)） | IC-Light 是**SD1.5 UNet**，两个变体 fc（前景）/ fbc（前景+背景）；输入前景被遮区域必须先涂灰，否则背景被遮/变暗（官方 README 明写） |
| **ControlNet 约束位置** | 用 depth/canny/openpose 锁构图，再让模型在框内生成 | 任意 ControlNet；`RegionAttention`/`BV` 系节点用 mask 代替 | ControlNet 不解决「谁是谁」，只解决「在哪里、什么姿态」 |

**注意**：`IC-Light` 与 `LayerDiffuse` 都是**按底模绑定的**（分别 SD1.5、SD1.5/SDXL/Flux）。它们不能「插到 H3 上」，只能作为**独立的后期工序**存在——这一点直接决定了第五节的分级。

### 3.3 身份一致性：四条路线的取舍

| 方法 | 训练需求 | 参考预算 | 身份强度 | 可编辑性 | 适用规模 |
|---|---|---|---|---|---|
| **角色 LoRA** | 10–30 图 / 500–2000 步 | 无（权重内化） | ★★★★ | ★★★★ | **长期固定 IP 角色**（主角、常驻 NPC）；单角色 20–150MB |

## 四、Multidiffusion / 区域注意力的实测口碑

**质量是否可接受**：可以，但有明确前提。

- MultiDiffusion 官方定位是「无需训练、把预训练模型外推到任意长宽比/分区控制」（[arXiv:2302.08113](https://arxiv.org/abs/2302.08113)）。落地口碑集中在**超分/外扩**，不是**多人分区**。
- 区域注意力的口碑集中在**「属性不串」**：Forge Couple 的 showcase 直接对比「有无 couple」；Attention Couple 被视为「标准答案」，但同一批节点描述反复出现同一句警告——**区域是软约束**。
- ARMD 的 README 把失败模式总结得最完整：独立 tile 会**各自发明结构**，导致 `visible seams / ghosting / 跨 tile 结构不一致 / tile 级色偏 / 重叠区语义冲突`；并提出 core/context/feather 三区分离。

**主要失败模式清单（按出现频率）**：

| 失败模式 | 触发条件 | 缓解 |
|---|---|---|
| 接缝网格（纹理相位跳变） | overlap 太小 / denoise 太高 / tile 数多 | 加 overlap、降 denoise、第二遍用半格偏移（[DOGMA Shift Pad](https://comfy.icu/node/DOGMAShiftPadV34) 就是这个思路） |
| 色偏 / 对比度漂移 | Tiled VAE `fast` 模式、GroupNorm 未跨 tile 归一 | 关 fast decoder、开 `color_fix`、用 colorfix 节点 |
| 幽灵 / 双头 / 双身 | 裁切块里上下文不足，模型补了第二个人 | 放大 context、`min_context_megapixels`、限制 tile 长宽比 |
| 角色变成碎片 | 区域小 + `mask bounds`（按区尺寸采样） | 换 `full image` 模式（约 3× 算力），或给角色 ≥1/4 画面 |
| 区域互相污染（提示词串味） | separation/strength 低、`until` 覆盖全程 | 调高 separation 但接受「拼贴感」；缩短 `until` 让后续步融合 |
| 未覆盖区出棕块/噪点 | 区域没铺满画布 | 补一个覆盖全图的 base region（Forge Couple 的 Global Effect 同理） |
| 蒸馏模型上「区域完全不生效」 | 模型是**单流 DiT**，没有独立 cross-attention | 见下节 |

### 5.1 先把本机硬事实摆清楚（全部源码/实测）

### 5.2 三分类判定

#### ✅ 可以直接用（不改代码、不改模型）

| 方案 | 为什么能直接用 | 注意 |
|---|---|---|
| **`<Picture 1..16>` 参考图编辑做「多人同框合成」** | 这是 H3 的原生能力，官方文档明确「第 1 张是被编辑的图，其余提供身份/道具/材质/构图」，最多 16 张 | 会占满上下文，出图变慢；8GB 卡上 4 张参考 + 16MP 约 4 分钟（社区实测） |
| **`H3Kit 高清分块采样`（H3-upgrade-kit）** | 本机就有，且是**唯一**针对 H3 逐 step tile 的实现；重叠窗是线性的，且能被显存自动规划 | **硬限制**：最多 8 块、单块长宽比 ≤2、ControlNet 不支持。它解决的是「显存不够」，不是「区域控制」 |
| **后期工序：裁切→采样→贴回** | 纯像素操作，与模型无关 | 本机没有 `Inpaint-CropAndStitch`，但插件自带 `JZImageUncropByMask` 已实现同样的「按 bbox 贴回 + 对称软边」（见 `docs/H3-IMAGE-局部重绘.md` §贴回），实测污染仅 2018/2048² 像素 |
| **Qwen-Image-Layered 做「事后分层」** | 节点在 0.45.0 核心里，官方模板可跑 | **要另外下 ~几十GB 权重**；它是「把成图拆层」，不是「给 H3 加 alpha」 |
| **`ImageCompositor` 图层栈 + `JoinImageWithAlpha`** | 内置，纯合成 | 需要你先有 alpha/mask |

#### ⚠️ 要改造（思路成立，但要写 H3 专属实现）

| 方案 | 为什么不能照抄 | 改造要点 |
|---|---|---|
| **区域提示词（ConditioningSetArea / Percentage）** | ① `//8` 坐标对 H3（16× VAE）差 2 倍；② 每个区一次前向，H3 遇到 batch>1 直接抛错 → 同尺寸的两个区会被 `can_concat_cond` 合并成一个 batch，**当场 500**；③ 单流 DiT 对「裁小 latent 再算」的方式没有空间先验（位置来自 RoPE 的 area-normalized 坐标，见 `model.py:_axis_from_sqrt_area`），裁一块出来等于告诉模型「这是一张独立的小图」 | 改用 `ConditioningSetAreaPercentage`（倍率无关）；或干脆不用内置 area，自己在 `optimized_attention_override` 里按 `minimax_h3_layout` 的 `img_pos` 做 **per-token 注意力 mask**（这是 `nodes_sparse_attention.py` 已经验证过的挂法） |
| **Attention Couple / Forge Couple / Region Genie** | 全都最终落到 `attn1/attn2` 的 `CrossAttention` 补丁上；H3 没有这个类 → **静默无效**（不报错，图照出，区域不生效）。MOSS-MultiID 在同类单流 DiT 上已经把这条坑写明：「`ConditioningSetMask`、`ConditioningSetArea`、Regional Prompter 这类节点依赖模型去读注意力遮罩，而这类模型不读——**它们不报错，但也完全不起作用**」 | 需要**新写一个 H3 区域引擎**：在 `optimized_attention_override` 里，对每个 region 构造 key/value 可见性 mask，按 `layout.segments` 的 `text`/`video` 段索引切分。工作量 ≈ 一个中型插件，且必须自己标定 `base_weight` / `end_percent` |
| **NAG（想给 H3 补回负面提示词）** | 两个独立阻断：① 需要 `cond_or_uncond` 同时含 0/1，而 `BasicGuider`（`nodes_custom_sampler.py:797`）**根本没有 negative 输入**；② 补丁挂在 `set_model_attn1_output_patch`，H3 不消费 | 必须换 `CFGGuider` 喂一个真 negative（多一次完整前向，6 步变 12 步等效），**并且**重写 NAG 的 patch 挂点。**成本极高、收益有限**——H3 官方立场是「把想避免的东西也写进正向提示词」 |
| **Tiled VAE 参数调优** | `VAEDecodeTiled` 的 `tile_size/overlap` 对 H3 被忽略（`vae.py:984-990` 直接 return `self.decode(z)`） | 想改 H3 VAE 的 tile 行为只能改 `MiniMaxH3VideoVAE(tile_size=...)` 构造参数，属于改模型代码 |
| **LayerDiffuse / AlphaVAE（想给 H3 原生 RGBA）** | 每个 LayerDiffuse 权重都是**针对某个底模训的 LoRA/透明 VAE**；H3 的 latent 是 24 通道 + patch 1×2×2，和 SDXL(4ch)/Flux(16ch) 完全不同构 | 等于重训一个 33B 模型的透明 LoRA + 透明 VAE 解码器。**不在可承受范围内** |
| **IC-Light 光照统一** | 是 SD1.5 UNet，输入通道数被改过（fc 多 4ch、fbc 多 8ch），只能配 SD1.5 | 只能作为**完全独立的第二套模型**跑在 H3 之外；本机没有 SD1.5 权重 |

#### ❌ 不适用（结构上就不成立）

| 方案 | 不适用原因 |
|---|---|
| **直接用 `ConditioningSetArea` 做 H3 的区域控制** | 坐标倍率错 + batch=1 硬限制，**必然出错或必然错位**。这不是「效果差」，是「算出来的区域不是你画的区域」 |
| **Attention Couple 系（PPM / prompt-control / Forge Couple）原样接 H3** | H3 无 `CrossAttention`，补丁挂不上；且这类节点的「负向压制」在 cfg=1 下没有载体 |
| **靠「提高 CFG / 写 negative」提升分区服从度** | H3 采样器无 negative 通道（`BasicGuider` 无 negative 输入，`guidance` 固定 1.0）；强行改 CFG 只会得到过饱和/结构崩坏（VSF 论文的反例） |
| **MultiDiffusion / Mixture of Diffusers 原版（comfyorg/comfyui-tiled-diffusion）** | 它是 MODEL patch，实现假设「4-D image latent（B,C,H,W）+ 每步可切片」。H3 是 `[B,24,1,h,w]` 且模型内 `pad_to_patch_size`，该包 README 里 **Regional Prompt Control 至今是未勾选**；DaSiWa 的同名节点文档也直接写「video models raise an error；ControlNet 不支持」 |
| **SpotDiffusion** | 官方标注 experimental / in testing，且设计目标是 panorama 提速，不是区域语义控制 |
| **Flux LayerDiffuse / Qwen 系节点直接套 H3** | 权重与结构都不通用；只能作为**另一个模型**并行使用 |

### 5.3 三档落地路线（按「投入/收益」排序）

**第 0 档｜零改造，今天就能用（推荐先做）**
1. **别为「分辨率」做分块**。H3-Image 原生 16MP，社区已有 8GB 卡跑满 16MP 的成熟工作流（`Draft 4MP → Full 16MP`，VAE 解码靠模型内部 tile）。分块的唯一正当理由是**显存**和**>16MP**，不是画质。
2. 多角色合成走 **`<Picture N>` 多参考编辑**：`Picture 1` = 底图/画布，`Picture 2..k` = 各角色立绘。这正好是官方文档给的用法（"put the man from Picture 1 into the café from Picture 2"）。
3. 局部修正走**已有 inpaint 链路**（`crop` 模式 + `JZImageUncropByMask`），已实测选区外污染 0.05% 量级。
4. 显存不够时才上 `H3Kit 高清分块采样`，并且**接受它只做「算力分摊」不做「区域控制」**。

**第 1 档｜小改造，收益明确**
1. **区域控制只走 `ConditioningSetAreaPercentage`**（倍率无关），并且**每个区尺寸必须互不相同**以避开 `can_concat_cond` 触发的 batch>1 崩溃——这是个很脏的规避手法，**推断**可行但我没实测，必须在真机上先验一次。
2. 分区后统一用一次 `ImageCompositeMasked` 级别的软边贴回，避免硬接缝。
3. 分层用**外挂模型**：Qwen-Image-Layered 拆层 → `ImageCompositor` 合成 → 需要 alpha 时 `JoinImageWithAlpha`。这条链不改 H3、不改 ComfyUI，只加权重。

**第 2 档｜真改造，需立项**
写一个 **H3 专属区域注意力引擎**：在 `optimized_attention_override` 里，用 `transformer_options["minimax_h3_layout"]`（`model.py:736` 每步都会写入）拿到 `segments` 与 `img_pos`，对每个 region 生成 key 可见性 mask；`end_percent` 控制从第几步开始放开。这是**唯一在结构上正确的 H3 区域方案**，且已有先例（`nodes_sparse_attention.py` 用的就是同一挂点）。
风险：① 33.1B 模型上每步多一份 mask 开销；② 需要在真机上标定 `base_weight`；③ H3 是 6 步蒸馏，**注意力分区在极短轨迹上的可控性没有先例**——这是全篇最大的未知数。

### 5.4 风险与验收建议

| 风险 | 严重度 | 说明 |
|---|---|---|
| **静默失效** | 高 | 区域补丁在单流 DiT 上「不报错、不生效」是已被 MOSS-MultiID 记录的现象。任何 H3 区域方案上线前必须做**「区域该生效但没生效」的检测**（例如两区颜色故意冲突，看是否真的分开） |
| **batch>1 崩** | 高 | `model.py:721` 是硬 raise。任何走「多 cond 同尺寸」的路径都要先验 |
| **6 步蒸馏 vs 注意力分区** | 高 | 少步模型的注意力分布与多步模型不同；FLUX 的区域方案论文都要额外调 `injection steps β`，6 步下 β 的可调空间极小 |
| **`//8` 类硬编码** | 中 | 不只 area，任何「按 SD 的 8× 下采样写死」的第三方节点在 H3 上都可能错位 |
| **Tiled VAE 参数被无视** | 中 | 调了没效果，容易误判为「参数不灵」 |
| **分层要换模型** | 中 | H3 无原生 alpha；分层必然引入第二套权重（几十 GB） |

**建议的验收实验（按顺序，每个都能证伪一个假设）**：
1. `ConditioningSetAreaPercentage` + `ConditioningCombine` 两区，尺寸**故意相同** → 预期触发 `batch size 1` 报错（验证 §5.2 的 batch 论断）。
2. 同上但两区尺寸不同 → 观察区域是否真的落在画对的位置（验证 16× vs 8× 的倍率问题在 percentage 版下是否消失）。
3. 用 Attention Couple 系节点接 H3 → 预期「图正常出、区域完全不生效」（验证 CrossAttention 缺失论断）。
4. `VAEDecodeTiled` 传 `tile_size=256` vs `1024` → 预期耗时/显存无差异（验证参数被忽略）。
5. 16MP 单张 vs 4 张 `<Picture>` 参考 → 记录耗时，确认多参考的边际成本。
