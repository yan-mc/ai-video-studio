## 一、DMAD 是什么（已核对官方源）

| 项 | 事实 | 来源 |
|---|---|---|
| 全称 | Distribution Matching as Adversarial Distillation | [GitHub](https://github.com/Yzmblog/DMAD) |
| 论文 | arXiv:2610.02188，2026-10-02 | 同上 |
| 作者 | Zhengming Yu 等（Texas A&M + **ByteDance**） | 同上 |
| 做法 | 把分布匹配**重铸为分类问题**：共享 backbone 上两个判别器头，用 logit 的线性损失训学生，**不需要维护辅助扩散模型** | 同上 |
| 产物 | H3 的 **rank-128 LoRA**，Diffusers 版 1.4 GB / ComfyUI 版 2.0 GB | [HF 模型卡](https://huggingface.co/ZhengmingYu/DMAD) |
| 三个学生 | `4step_lora_critic`（论文版）、`4step_full_critic`（AVGen-Bench 更高）、**`8step_full_critic`**（从零按 8 步训，2026-10-29） | 同上 |
| ComfyUI 转换 | **精确转换，无降秩**（"exact conversion"） | 同上 |

社区另有一个 Kijai 的 `avg_rank_39` 降秩版（367 MB）——**不是**官方，[ComfyUI Wiki](https://comfyui-wiki.com/zh/news/2026-10-02-dmad-h3-4step) 明确提示"其降秩方式与键布局并非论文所评估的对象"。本项目用的是**官方精确转换版**。

## 二、DMAD 与 H3 的接口（关键结论）

### 2.1 挂载方式：就是一个普通 LoRA

```
UNETLoader → LoraLoaderModelOnly(dmad_..._comfyui.safetensors, strength=1.0)
           → MiniMaxH3SigmaShift(shift_video=12, shift_audio=2)
           → 采样
```

**没有任何自定义节点**（除了可选 `comfyui/ComfyUI-DMAD` 里的等价节点）。官方明确：用 stock `lcm` + `simple` 就够。

### 2.2 参数对照（这是最容易错的地方）

| 项 | DMAD | LightX2V（本项目原方案） |
|---|---|---|
| LoRA 数量 | **1 个通用**（ref/fl2v 通吃） | **2 个专用**（ref 一个、fl2v 一个，不通用） |
| 采样器 | **`lcm`** | `euler` |
| 调度器 | `simple` | `simple` |
| 步数 | 4（4step 学生）/ **8**（8step 学生） | 4 |
| CFG | 1.0（已是 guidance-distilled） | 1.0 |
| 视频 shift | 12 | ref:12 / fl2v_768p:**6** |
| 音频 shift | **2** | 3 |

⚠️ **两个必需显式设的值**：DMAD 的音频 shift 是 **2**（模型默认是 3）；LightX2V 的 FL2VA **768p** LoRA 训练在 **6**（项目原来用模型默认 12，是错的）。

### 2.3 shift 为什么会错，以及为什么必须插节点

ComfyUI 的 `supported_models.py` 里 `MiniMaxH3` 写死：

```python
sampling_settings = { "shift": 12.0, "audio_shift": 3.0 }
```

这是**未蒸馏原模型（50 步）**的取值。每个蒸馏 LoRA 是在特定 shift 上训出来的。用错了**不会报错**，只是 sigma 网格与训练分布错位 → 静默变糊/动作变差。

所以：**只要方案声明了 shift，就必须插 `MiniMaxH3SigmaShift`**。

实测 sigma 序列（`simple`，shift=12）：

| 步数 | sigma |
|---|---|
| 4 | 1, .973, .923, .800 → 0 |
| 8 | 1, .988, .973, .952, .923, .878, .800, .632 → 0 |
| 16 | 1, .994, .988, .981, .973, .964, .952, .939, .923, .903, .878, .845, .800, .735, .632, .447 → 0 |

**16 步不是 8 步的细分**，而是整条曲线重采样 → 训练点对不上。这是"多加步数反而变差"的机制解释。

`audio_shift` 完全不改变 video sigma —— 它只改 `audio_scale = shift/audio_shift` 这一个标量（2→6.0，3→4.0），该标量被传给 DiT 缩放音频目标。

## 三、DMAD 是否改变输入格式/数量要求？

**结论：完全不改变，实测确认。**

DMAD 只是 transformer 上的权重补丁，不碰 tokenizer、不碰 conditioning 节点。做了两轮探针（`scripts/dmad_capability*.mjs`）：

| 输入 | DMAD 下 | 说明 |
|---|---|---|
| 参考图 1 张 | ✅ 接受 | |
| 参考图 2 张 | ✅ 接受 | |
| 参考视频（`LoadVideo`→`GetVideoComponents`） | ✅ 接受 | |
| 参考音频（`LoadAudio`） | ✅ 接受 | |
| 图 + 视频 + 音频混合 | ✅ 接受 | |
| 首尾帧（`MiniMaxH3ImageToVideo`） | ✅ 接受 | |
| 非法帧数 130 | ⚠️ **也接受** | ComfyUI 不校验 17k+5，**由插件层负责** |
| 非 32 倍数分辨率 1000 | ⚠️ **也接受** | 同上 |

所以这些约束（图 ≤9 / 视频 ≤3 / 音频 ≤3 / 总 ≤12 / 帧数 17k+5 / 分辨率 32 倍数 / 提示词 ≤7000 字）**与选哪个加速方案无关**，全部由插件层维持 —— 现有逻辑无需改动。

## 五、对照实测数据（选 DMAD 的依据）

同一提示词（`F:\AI视频\临时\promote.txt`，6044 字符）+ 两张参考图 + 同 seed，只换加速方案：

| 组 | LoRA | 采样器 | 步数 | 清晰度 | 帧间差 | 跳切 | 音频动态 |
|---|---|---|---|---|---|---|---|
| R1 | LightX2V | euler | 4 | 347 | 9.05 | **3** | 4.0 dB |
| R2 | LightX2V | lcm | 4 | **516** | 15.53 | 0 | 2.6 dB |
| R3 | **DMAD 8step** | lcm | 8 | 171 | 20.25 | **0** | 4.2 dB |
| R4 | DMAD 4step | lcm | 4 | 140 | 5.76 | 0 | **12.6 dB** |

**关键观察**：
- R3 的**角色形态还原最好**：螺旋羊角、羊尾、侧坐姿态都能分辨；LightX2V 的角糊成色块。
- R1 有 **3 次跳切**，违反提示词的 `one continuous take`；DMAD 两组都是 0 次。
- LightX2V 的**边缘更锐**（清晰度指标更高）—— 这是它的真实优势，所以保留为回退方案。

> 上一轮我曾用"清晰度"单一指标判定 DMAD 更差，那是**评判标准错误**：高对比平涂画面下该指标主要反映边缘锐度，不反映内容理解。这一轮换用复杂提示词后结论反转。

## 七、仍需注意

1. **DMAD 8 步比 LightX2V 慢约 45%**（200s vs 140s @864×480/124帧）。这是质量换时间的直接代价。
2. **本机没有 H3 latent upscale 模型**（`models/latent_upscale_models/` 是空目录），所以真正的"两阶段放大"（低步出基础→放大 latent→低 sigma 精修）暂时做不了。若要做，需先找 H3 的 latent upscale 权重。
3. **DMAD 官方没有"双采样"工作流** —— 官方只给 4step/8step/8GB 三个单阶段流程。所谓"双采"是社区做法，可套在任何 LoRA 上，不是 DMAD 专属。
4. **12GB 卡上 DMAD 8 步是当前甜点**：官方说 8step 是"clear step up"，实测耗时也能接受。
5. 角色卡 traits 仍是中文并拼进英文正文（`with 金发、紫瞳…`），属标签值位置，未改。
