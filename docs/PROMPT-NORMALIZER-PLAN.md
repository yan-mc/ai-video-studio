# 提示词规范化方案（NSFW 换人场景）

> 问题：换人流程要求六段式英文提示词，但实际使用者经常要写 NSFW 内容 ——
> 云端 AI 普遍拒绝生成这类文本，只能人工手写。手写出来的往往是
> 自由格式中文/中英混排，结构全丢（实测 802 字里六段全部缺失、中文占 32.5%）。

## 一、先厘清一件事

**用户不是在要求"帮我写黄文"，而是在要求"把我已经写好的内容整理成结构化格式"。**

这两件事的技术难度和合规风险完全不同：

| | 生成内容 | 重排格式 |
|---|---|---|
| 需要理解 | 语义（要"想得出"做什么） | 结构（把已有文本拆进六个字段） |
| 模型要求 | 大模型 + 内容能力 | **小模型够用**，甚至规则引擎够用 |
| 云端可否 | 多数拒绝 | **多数接受**（输入已是既成文本） |

所以正确方向是 **格式重排 + 结构化填充**，不是"让模型创作"。

## 二、三个可选方案

### 方案 A：规则引擎（零依赖，推荐先做）

不调用任何模型，纯字符串处理：

1. 按 `<Subject N>` / `<Video N>` / `<Picture N>` 标签切分
2. 按行特征归类：
   - 含「替换成 / 复刻」→ `summary`
   - 含 `<Subject \d> 是` → `subject_definitions`
   - 含「全程保持 / 完全一致」→ `retention_analysis`
   - 含 `[Shot N]` 或「注意 / 强调」→ `detailed_description`
   - 其余 → 追加到 `detailed_description` 末尾
3. 用固定英文模板包裹，用户原文**作为注释保留**

**优点**：零成本、可预测、不涉及模型拒答
**缺点**：不做中译英，中文原句仍留在正文里

### 方案 B：本地小模型（3B–7B，离线）

本机已有 `torch 2.11.0+cu128` + `transformers 5.22.2`，可直接跑。

候选模型（按显存占用从小到大）：

| 模型 | 参数量 | 显存(4bit) | 中文 | 备注 |
|---|---|---|---|---|
| Qwen2.5-3B-Instruct | 3B | ~2.5GB | 强 | 最省，格式重排够用 |
| Qwen2.5-7B-Instruct | 7B | ~5GB | 强 | 质量明显更好 |
| GLM-4-9B-chat | 9B | ~6.5GB | 强 | 中文最强 |
| Mistral-7B | 7B | ~5GB | 弱 | 不建议（中文差） |

**关键优势**：本地模型**没有拒答机制**（没有 RLHF 安全对齐到那一步），
它就是纯粹的下一个 token 预测器。

**成本**：首次下载 2–14GB；每次推理 2–10 秒。

**风险**：小模型 3B 处理复杂指令时容易漏项，7B 更稳。

### 方案 C：复用 DSH 内置 LLM（零下载）

项目已有 `callText(ctx, cfg, {system, user})`（`host/services/nanfeng/dsh-llm.js:182`），
走用户已登录的 DSH 模型，**不需要任何 API Key**。

**优点**：零下载、质量最高
**缺点**：**很可能被拒**（取决于当前用的模型）
**适用**：把系统提示词写成"你是格式转换器，输入是已完成文本，
你只做字段拆分，不新增内容" —— 有一定概率绕过内容审查，
因为任务描述听起来是无害的格式整理。

## 三、建议：三层降级

```
用户写中文自由文本
   ↓
① 规则引擎先切（保证永远能出结果）
   ↓ 若成功 → 用
   ↓ 若切分质量差
② 试 DSH 内置 LLM（零成本，可能被拒）
   ↓ 被拒
③ 本地 7B 模型（离线，必定成功）
   ↓
输出六段式英文提示词
```

这样：
- **永远有兜底**（规则引擎不会失败）
- **不花钱**（DSH 内置 + 本地模型都是零边际成本）
- **不依赖外网**

## 四、具体实现要点

### 4.1 保留用户原文

无论走哪条路，都要把用户原始输入**保留在 `job.params.promptOriginal`**，
并在最终提示词末尾用注释形式附上：

```
<!-- 用户原文备份（供核对，模型请忽略） -->
```

这样出了问题能追溯，也避免"AI 改写后原意丢失"。

### 4.2 LoRA 触发词不能动

用户提到的：

```
Video depicts a sexual scene between a female central character and a
massive, giant partner that inserts it's giant erect penis into woman vagina
```

这是 **DR34ML4Y 的启动词**（模型训练时绑定的描述句）。
它**必须原样保留**，不能被"优化"或翻译。

处理规则：识别出这类句子（长描述 + 无 `<Subject>` 标签 + 位于开头）
→ 标记为 `trigger_phrase`，**逐字保留**在 `detailed_description` 开头。

### 4.3 中译英是有损的

如果用户写「强调huge insertion + stomach bulge」，翻译成英文会丢失细微差别。
建议：**保留中文原句在后面**，前面加英文翻译。

```
[Shot 1] Emphasize the huge insertion and stomach bulge.
（原文：强调huge insertion + stomach bulge）
```

H3 对中英混排有一定容忍度，但**主体结构必须英文**。

### 4.4 小模型的提示词设计

```
你是一个格式转换器，不是内容创作者。

任务：把用户提供的描述拆分到六个字段中。
规则：
1. 只做拆分和翻译，不新增、不删减、不评价内容
2. 用户给的触发词必须逐字保留在 detailed_description 开头
3. 输出纯英文，中文原句用括号附在对应英文句后
4. 六个字段必须齐全：subject_definitions / summary /
   retention_analysis / detailed_description /
   overall_soundscape / non_diegetic_music

用户输入：
{user_prompt}

输出（仅六段式，不要任何解释）：
```

**注意**：不要写"这是NSFW内容"，就当成普通文本处理。
任务描述越中性，拒答率越低。

## 五、性能与资源

| 方案 | 首次耗时 | 每段耗时 | 显存 | 磁盘 |
|---|---|---|---|---|
| 规则引擎 | 0 | <10ms | 0 | 0 |
| DSH 内置 | 0 | 3–15s | 0 | 0 |
| Qwen2.5-3B | 下载 6GB | 2–4s | 2.5GB | 6GB |
| Qwen2.5-7B | 下载 15GB | 4–8s | 5GB | 15GB |

**注意显存冲突**：本地模型和 H3 同时跑会抢显存。建议：
- 提示词处理用 **CPU 推理**（3B 模型 CPU 上 10–20 秒，可接受）
- 或在 H3 渲染间隙处理

## 六、不建议的做法

| 做法 | 为什么不建议 |
|---|---|
| 用 3B 模型"生成"动作描写 | 小模型创作能力弱，会写出很空洞的句子 |
| 让模型"润色" NSFW 内容 | 必然拒答，白等 |
| 全自动不保留原文 | 出问题无法追溯 |
| 下载更大的模型（>14B） | 显存吃不消，且收益有限 |

## 七、当前建议动作

**先做方案 A（规则引擎）**，因为：

1. 它不依赖任何外部资源，今天就能用
2. 用户手写的内容其实**已经有结构**（`<Subject 1> 是...` 这种），
   规则切分成功率比想象中高
3. 等规则引擎跑起来、看到真实失败率之后，再决定要不要加本地模型

如果规则引擎的切分质量不够（比如用户写得很随意），再上 **7B 本地模型**。
