## 一、问题诊断

### 现状

当前 `client.js` 把整个「导演台式工作台」塞进 DSH 侧栏面板：

```
DSH 窗口 844 CSS px（175% DPI）
├── DSH 侧栏 286 px
└── 插件面板 558 px
    ├── 左栏 150 px
    ├── 中间舞台 326 px   ← 只能这样
    └── 右栏 0 px（自动收起）
```

**根本矛盾**：画布节点式工作流需要 **1600+ px** 宽度，DSH 侧栏结构上给不了。

### 结论

不是「把 UI 做得更紧凑」能解决的，**必须换承载容器**。

### 关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 操作页承载 | **浏览器标签页** | 全屏、可多开、可拖到第二显示器 |
| 独立窗口 | `window.open()` 可控尺寸 | 六导演台各开一个 |
| **导演台前端** | **直接复用解包产物**（`studio-apps/director`） | 已验证可用，零错误，交互与原版一致 |
| 其余前端（画布/素材库/剧本） | **React + React Flow** 新建 | 这些页面没解出来，且画布是核心，自己写更可控 |
| 后端 | **现有 index.js 扩展** | 工具和 API 复用，只加 HTTP 静态服务 |
| 启动器 | DSH 插件面板（小） | 保持「点进去」的入口感 |

### 为什么不用 Electron/Tauri 自建壳

- 用户已有 DSH，再加一个桌面壳是重复建设
- 浏览器方案零安装、可远程访问、调试方便
- 原版用 Tauri 是因为它要卖给终端用户；我们自用，浏览器足够

## 三、改造范围

### 3.1 后端（index.js）

**保留**：12 个 `studio_*` 工具、生成编排、预演引擎调用、ffmpeg 后处理

**新增**：
```
GET  /studio/                     → 返回主 SPA 的 index.html
GET  /studio/assets/*             → 静态资源（JS/CSS/字体）
GET  /studio/api/monitor          → 监测数据聚合（服务状态/显存/队列/磁盘）
GET  /studio/api/canvas/:projectId → 画布数据（节点+连线+视口）
POST /studio/api/canvas/:projectId → 保存画布
```

**关键点**：静态服务要监听在 DSH 的 webServer 上（复用现有端口），
路径前缀 `/ai-video-studio/studio/`，避免和其他插件冲突。

### 3.2 前端（全新 client）

**拆成两个产物**：

| 产物 | 用途 | 体积 |
|---|---|---|
| `launcher.js` | DSH 面板里的启动器 + 监测器 | 小（~30 KB） |
| `studio/` | 浏览器 SPA（画布 + 各页面） | 大（需构建） |

**问题**：现在 `client.js` 是手写的 `React.createElement`（无 JSX、无构建）。
SPA 规模大，**必须上构建**（Vite）。

**方案**：
```
工作室/dsh-ai-video-studio/
├── index.js              Host（工具 + API + 静态服务）
├── launcher.js           启动器（手写 createElement，小）
├── studio-src/           SPA 源码（React + TS + Vite）
│   ├── src/
│   │   ├── main.tsx
│   │   ├── canvas/       画布（React Flow）
│   │   ├── pages/        素材库/剧本/导演台/剪辑
│   │   ├── nodes/        26 种节点
│   │   └── api/          HTTP 客户端
│   └── vite.config.ts
└── studio-dist/          构建产物（提交进仓库）
```

**注意**：DSH 插件规范要求 `exports` 里的 `./client` 指向单个 JS。
启动器保持手写，SPA 独立构建后由 Host 静态服务托管。

### 3.3 数据模型

从「项目/镜头」扩展到「项目/画布/节点/素材」：

```js
Project {
  id, name, type,          // 短剧/漫剧/电商/自由
  canvas: {
    nodes: [ { id, type, position, data, ... } ],
    edges: [ { id, source, target, ... } ],
    viewport: { x, y, zoom }
  },
  assets: { character: [], scene: [], prop: [], ... },
  episodes: [ { id, name, shots: [] } ]
}
```

**兼容**：现有 `shots` 数据可平滑迁移为「分镜节点」。

## 五、需要你确认的决策

### Q1：技术栈
- **A（推荐）**：React + React Flow —— 与现有 client.js 同语言，生态最成熟
- B：Vue + Vue Flow —— 更贴近原版，但要重写现有代码

### Q2：构建产物是否进仓库
- **A（推荐）**：进仓库（`studio-dist`），这样别人 clone 下来直接能用
- B：不进仓库，用户自己 `pnpm build`

### Q3：启动器形态
- **A（推荐）**：菜单列表 + 状态灯（信息密度高）
- B：卡片网格（更像应用商店）
- C：保留缩略画布预览 + 菜单

### Q4：独立窗口 vs 标签页
- **A（推荐）**：默认新标签页，导演台用 `window.open` 独立窗口
- B：全部标签页
- C：全部独立窗口

### Q5：PDF/图片素材的处理优先级
原版有 14 个图像工具。你要**全部**还是先做最常用的？
- **A（推荐）**：先做 裁剪 / 切割分镜 / 标注 / 抠图 4 个
- B：14 个全做

## 六、风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **构建链引入** | 插件从「无构建」变「要构建」，复杂度上升 | 产物进仓库，用户不构建也能用 |
| **React Flow 学习曲线** | 画布交互细节多 | 先做最小可用，逐步加 |
| **26 种节点工作量大** | 每个节点都要 UI + 后端 | 先做 3 个跑通，其余按需 |
| **图像生成能力缺失** | 原版 14 个工具依赖图像模型，我们只有 H3（视频） | 需部署 H3-Image 或接 API |
| **TTS / 音乐模型缺失** | 配音、BGM 做不了 | 需另行选型 |

## 附：从对标软件学到的设计原则

1. **产物是新节点，不覆盖原图** —— 鼓励试错
2. **提示词是编译的，不是模型直接写的** —— 同输入必同输出
3. **撤销步数要够**（原版 12 步，AI 导演台 50 步）
4. **门禁是体检不是闸** —— 未过也能导出，报告说清差多少
5. **自动保存（拖拽结束才落盘）** —— 不卡帧
6. **变体链** —— 多版本留痕，一键选当前
7. **分段生成，不是一口气生成整片**
